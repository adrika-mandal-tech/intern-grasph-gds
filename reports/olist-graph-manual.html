A copy of the Grasph database that holds the Olist graph, to run on your own computer. How a row becomes a node, and a column becomes a relationship

  1. One node for each key. The pipeline makes one node for each different value of the key column. Two rows with the same key become one node. This is why 1,000,163 geolocation rows became 19,015 nodes: the file has many map points for each zip-code area, and the node keeps one of them.
  2. Each other column becomes a property. The column name is the property name. The node also gets namespace (always olist) and source (the file name).
  3. A shared column becomes a relationship. The schema says: "customer_id in Order points at customer_id in Customer". The pipeline makes one PLACED_BY relationship for each pair of nodes where the two values are equal.
  4. No match, no relationship. When the value does not exist on the other side, the node stays and the relationship is not made. TASK 11.3 lists how many times this happened.
Key and foreign key
SIMPLE

The key is the name tag of a row: no two rows have the same one. A foreign key is a column that holds the name tag of a row in a different file. "This order belongs to customer X."

TECHNICAL

Primary key: the column or columns under a RequireUniqueId constraint in the schema. Foreign key: the from_columns and to_columns of a relationship schema. The relationship is the equi-join of the two labels on those columns.

The key columns stay on the nodes as properties. An OrderItem node has order_id, product_id and seller_id as text, and it also has the three relationships. The relationship and the property say the same thing.

No relationship has a property. There is no weight, no date and no amount on a link. When an algorithm needs a weight, you make it from the nodes: the price of the OrderItem, or a count (how many items, how many shared products).

Direction
SIMPLE

Each link is stored as an arrow, from one thing to the other. "Order → Customer" does not mean that you cannot walk from the customer to the order. It is only the way the arrow was written down.

TECHNICAL

The direction is the one in the schema (from_label → to_label). For most algorithms on this graph you project the relationships as undirected, the same as orientation: 'UNDIRECTED' in Neo4j GDS.

TASK 11.5Know nine facts before you run anything

An algorithm does not know these facts. It gives you a number in each case. You must know them, so that the number means something.

  1. A Customer node is not a person. Olist gives a new customer_id for each order. So there are 99,441 customers for 99,441 orders, and each Customer node has exactly one order. The person is customer_unique_id: 96,096 people. To study people, group the Customer nodes by customer_unique_id first.
  2. Almost nobody buys two times. 93,099 people have one order. Only 2,997 people (3.1%) have two or more. A "customers who bought from the same seller" graph is very thin for this reason.
  3. Most orders have one item. 88,863 orders have one item. Only 3,236 orders have two or more different products, and only 1,278 orders have two or more sellers. A "bought together" graph is small.
  4. A few sellers do most of the business. Half of the sellers sold 8 items or fewer. The top 30 sellers (1%) sold 26.4% of all items. Half of all items come from 131 sellers.
  5. Most products are sold by one seller. Only 1,225 of 32,951 products are sold by two or more sellers. A shared product is one of the few things that joins two sellers to each other.
  6. Zip codes lost their first zero. The server holds the zip prefix as a number, so 01037 became 1037. This is so for 23,995 customers, 1,027 sellers and 4,354 areas (all of them in the state of São Paulo, most in and around the city). The relationships are correct, because both sides lost the zero. To print a real zip code, write it with 5 digits: str(z).zfill(5).
  7. 623 products have no category node. 610 products have an empty category. 13 products are in two categories that the translation file does not have (pc_gamer and portateis_cozinha_e_preparadores_de_alimentos). These 623 products are in no category projection.
  8. A review can lose an order. The review file has 99,224 rows and 98,410 different review ids: the same review is sometimes written for several orders. The node keeps one row, so it links to one order only. In total 1,274 orders have no review node: 768 have no review in the source file, and 506 lost theirs in this way.
  9. The graph has no triangles. No three labels are joined to each other in a ring. So triangle count and the clustering coefficient are zero on the stored graph, for every node. These two measures can only become useful on a projection that joins nodes of one kind to each other.

The first and the last months are almost empty: 4 orders in 2016-09, 1 in 2016-12, 16 in 2018-09, 4 in 2018-10. Do not read a trend from them. The months with full data are 2017-01 to 2018-08.

TASK 11.6Start Grasph on the dump

You need about 4 GB of free disk and 4 GB of free memory. The steps below are for Windows. The steps for a Mac follow them.

  1. Unpack the dump. It becomes a folder named grasph-data (2.8 GB). 
    tar -xf olist-grasph-store.tar.xz
  2. Give the server a placeholder model key. The server will not start without a value in OPENAI_API_KEY. For graph queries the value is never used, so any text is fine. Do not put a real key here. 
    $env:OPENAI_API_KEY = "sk-not-a-real-key"
  3. Start the server on the folder, with the limits raised (see below why). 
    Windows (PowerShell):
bin\graphdb-server.exe --port 7474 --admin-password olist-local-1 `
  --data-dir grasph-data --native-data-dir grasph-data\native-data `
  --query-timeout-secs 3600 --max-path-bindings 5000000 `
  --max-materialized-bindings 5000000 --max-result-rows 5000000
    Wait for the line Grasph ready - listening on 127.0.0.1:7474. The first start does two jobs one time only: it builds the text index again from all 568,960 nodes, and it builds a vector index for the namespace (the log counts up to 128,136). Allow 15 minutes and do not close the window. A later start takes a few minutes. Leave the window open: the server runs in it. Stop it with Ctrl+C.
  4. Check it, in a second window. 
    $env:GRASPH_PASSWORD = "olist-local-1"
python grasph_client.py
    It must print 'node_count': 568960, 'relationship_count': 774266 and the nine labels with their counts. This takes about a minute.

On a Mac: run the Linux program in Docker

There is no Grasph program for macOS. The folder has the Linux program of the demo server and the libraries that it needs. Docker runs them on a Mac. Install Docker Desktop, unpack the dump as in step 1, and then, in the Terminal, in this folder:

Then check it in a second Terminal window: GRASPH_PASSWORD=olist-local-1 python3 grasph_client.py

On a Mac with an Apple chip, Docker translates the program, so expect it to be slower. If it does not start, send the last lines that it printed.

TASK 11.7Query the data in Grasph

Grasph speaks GQL, and most Cypher that you know works as it is. You send a query over HTTP and you get rows back.

StepRequestReply
Log inPOST /api/v1/auth/login with {"username": "admin", "password": "…"}{"token": "…"}
QueryPOST /api/v1/query with {"query": "MATCH …"} and the header Authorization: Bearer <token>{"columns": […], "rows": [[…], …], "row_count": n, "truncated": …}

In Python, grasph_client.py does both steps:

from grasph_client import Grasph

g = Grasph(password="olist-local-1")
reply = g.query("MATCH (o:Order) RETURN o.order_status AS status, count(o) AS orders ORDER BY orders DESC")
reply["columns"]      # ['status', 'orders']
reply["rows"]         # [['delivered', 96478], ['shipped', 1107], ...]

All six ran on the dump with the Windows program on 2026-10-08. The first five take from under a second to 16 seconds. The last one took 19 seconds.

Four rules for queries on this server

  1. Return properties, not whole nodes. RETURN s sends each property of the node, and 128,136 nodes have a vector of 1,536 numbers for the text search: about 20 KB of text for each node. Write RETURN s.seller_id, s.seller_city.
  2. Name the label on each node of a pattern. MATCH (o:Order)-[:HAS_ITEM]->(i:OrderItem) starts from one label. MATCH (n) with no label reads all 568,960 nodes into memory.
  3. To draw a relationship or to get its ends, return it. RETURN r gives {"id", "from", "to", "rel_type", "properties"}, where from and to are node ids. id(n) gives the id of a node.
  4. Expect some queries to be slow. A read of the whole Customer label takes about eight times as long as a read of the Order label, which has the same number of nodes (40 seconds against 5 in our test). A pull of one whole relationship type takes about a minute. This is a known weakness of this build, not an error in your query.

What you find slow, wrong or missing while you work is useful to the team. Write it down with the query and the time. Grasph is the product: a clear report of a problem in it is a result.

TASK 11.8Pull data into Python and run an algorithm

With Neo4j, the projection and the algorithm ran inside the server. Grasph has no GDS library today. So you pull the nodes and relationships that you need out of Grasph, and the projection and the algorithm run in your Python program.

What you did with Neo4jWhat you do here
GraphDatabase.driver("bolt://…")g = Grasph(password=…)
session.run("MATCH …")g.query("MATCH …")
gds.graph.project('g', labels, types)g.rels("TYPE") for each type that you need, then build the graph in a graph library (NetworkX, igraph)
A Cypher projection over two or three hopsA query that returns the two end ids of the path: MATCH (s:Seller)<-[:SOLD_BY]-(i:OrderItem)-[:ITEM_OF_PRODUCT]->(p:Product) RETURN id(s), id(p)
CALL gds.<algorithm>.stream(…)The function of the graph library. You choose the library and the function.
.write back to the graphSave a file with the node id in the first column. Writing results back into Grasph is not part of this work.
g = Grasph(password="olist-local-1")
g.schema("olist")                 # labels, properties, relationship types and their key columns
g.label_counts("olist")           # {'Customer': 99441, 'Geolocation': 19015, ...}
sellers = g.nodes("Seller")       # [{'_id': 564843, 'seller_id': '3442f8...', 'seller_city': 'campinas', ...}, ...]
sold_by = g.rels("SOLD_BY")       # [{'id': ..., 'from': <OrderItem id>, 'to': <Seller id>, 'properties': {}}, ...]

g.nodes(label) asks for the properties by name, so the vectors never travel. In our test a whole label came in 1 to 40 seconds and a whole relationship type in 45 to 100 seconds.

Projection
SIMPLE

You decide what counts as a connection, before any algorithm runs. "Both sellers are in the housewares category" and "both sellers sell the very same product" are two different connections, and they give two different graphs.

TECHNICAL

The sub-graph that an algorithm sees: chosen labels and relationship types, often with a path of two or three hops made into one edge, and often with direction dropped. On this schema the stored graph is rarely the right input as it is: see the facts in TASK 11.5.

TASK 11.9Report a result that others can trust

A graph algorithm always returns a number. These six rules separate a number from a finding.

  1. Name the projection. Write which labels and relationship types the algorithm saw, and the number of nodes and edges of that graph. "Louvain on Olist" is not a method.
  2. Run each random method with several seeds. Louvain, Leiden, sampled betweenness and label propagation start from a random state. Report the range over the runs, not one run.
  3. Put a simple count next to each score. When a centrality score gives the same order as a plain count of links, say so. The simple count is then the result.
  4. Ask whether chance gives the same. Shuffle the thing that you test and compute the number again, many times. Your number is a finding only when the shuffled numbers are rarely as large.
  5. Say how many. "28% of 65 pairs" and "28% of 65,000 pairs" are not the same strength.
  6. Check your pull against Grasph. Count the same thing with a query on the server, as the example does. When the two numbers differ, the error is in the pull or in the projection.

TASK 11.10Know the answers to the common questions

If you ask

"Can I connect to the demo server?"

No. You have the same database on your own computer. Work there.

"Can I use my Neo4j GDS code?"

The queries, mostly yes. The gds.* calls, no: Grasph has no GDS library today. The table in TASK 11.8 shows what replaces each step.

"The server does not start."

Read the last lines that it printed. The three usual causes: OPENAI_API_KEY is not set in that window; --admin-password is missing; or a second server already uses the folder or the port.

"My query returned exactly 10,000 rows," or fewer rows than I expect.

The server was started without the raised limits, and the result was cut. Stop it and start it with the command in TASK 11.6.

"Why are there as many customers as orders?"

Olist gives a new customer_id for each order. Use customer_unique_id for the person: 96,096 people.

"My count of reviews is different from what I read about this dataset."

The file has 99,224 rows and 98,410 different review ids. The graph has one node for each id.

"My zip codes have four digits."

The first zero was lost, because the server holds the prefix as a number. Write str(z).zfill(5).

"Is this real data?"

Yes. They are real orders, which Olist made public after it removed the names of people, shops and products. So there is no name to show: a seller is an id, a city and a state.
