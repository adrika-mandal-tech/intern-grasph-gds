Why

TASK 08 - Time Series & Spatial Analysis (P8)

Why
PURPOSEAnalyse temporal/trend dynamics and shipping economics. The critical first move is getting the analysis window right, because the boundary months are near-empty and would distort any trend.
OBJECTIVEQuantify the freight-vs-distance/weight/price relationship and test delivery-time vs distance. Validate the trend window before modelling.

Why the window matters first: The raw span is 2016-09 → 2018-10, but the boundary months are near-empty and must be excluded, otherwise any trend is driven by <0.1% spikes:

Boundary months (DROP before modelling): 2016-09 = 4 orders · 2016-12 = 1 · 2018-09 = 16 · 2018-10 = 4. The valid trend window is 2017-01 → 2018-08 (20 full months). Modeling outside this window would let 4-order months masquerade as real seasonality.

Observed trend (freight elasticity & delivery time): Distance elasticity ≈ 0.190, weight ≈ 0.155, price ≈ 0.104; R²(distance-only) ≈ 0.289 vs full-model ≈ 0.542. Delivery-days vs distance Pearson r ≈ 0.393. No single month dominates freight — the trend is stable inside the clean window, so the elasticity estimates are window-safe.

Temporal validity note: Because the boundary months are dropped, all conclusions below (seasonality, elasticity, delivery-time correlation) apply to the 2017-01→2018-08 window only.

How: Executed task08_timeseries_spatial.py. First established the valid window above; then computed great-circle distance between each customer's and seller's ZIP centroids using the haversine formula (proven in proof #9). Log-log OLS for freight economics; Pearson correlation for delivery time. Monthly aggregation then runs only inside the clean window.

Best Practice for Analysis

RULE (TASK 11.9 rule 6): Cross-check your pull against Grasph. Count same thing with a server query - if numbers differ, error is in pull/projection, not algorithm.

CRITICAL: Never return whole nodes with vectors. Use property projection: RETURN s.seller_id, s.seller_city not RETURN s. Vectors (1536-d) make results huge.

LIMITS: With defaults (10k rows), results truncated - check "truncated": true in response. Use raised limits (5M) for full pulls.

Q&AAnswers to Common Questions

Dataset & Schema

Q: How large is the Olist dataset?

A: 568,960 nodes, 774,266 relationships across 9 labels (Order, Customer, OrderItem, Payment, Review, Product, Seller, Geolocation, ProductCategory). 1.55M source CSV rows.

Q: Are there really 99,441 customers for 99,441 orders?

A: Yes - Olist gives a new customer_id per order. The real person is customer_unique_id with 96,096 distinct values.

Q: Why does the graph have no triangles?

A: Mathematically proven (Proof #6). No three labels are pairwise connected - so no 3-cycle possible regardless of nodes. Must project to same-label nodes to get triangles.

Q: What about duplicate reviews/zip codes?

A: 99,224 review rows → 98,410 unique review_id (1 node per id). 1M+ geolocation rows → 19,015 zip prefixes (1 node per prefix).

Q: Why do zip codes look like "1037" instead of "01037"?

A: Stored as numbers in the server; São Paulo zips lost leading zero. Use str(z).zfill(5) to restore proper format.

Analysis Results

Q: How accurate is late delivery prediction?

A: AUC=0.7758, AP=0.2466 (vs prevalence 0.065). So significantly better than random. Driven by purchase-time features.

Q: Is the power law real?

A: For seller item-incidence: α=2.381, KS p=0.59 - fails to reject power law. Vuong test shows power law beats lognormal and exponential (p=0.000).

Q: Why is bought-together prediction weak?

A: Only 3.3% of orders have ≥2 distinct products. Structural limitation. Association rules still find high-lift pairs but very low support.

Q: How strong are the seller communities?

A: seller_shared_categories: Q=0.356±0.002 (6–7 communities). Null model Q=0.029±0.0007, permutation p≤0.05 - statistically significant.

Q: Does text sentiment match ratings?
